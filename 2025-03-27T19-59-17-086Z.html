What is grpc?

gRPC (Google Remote Procedure Call) is an open-source, high-performance framework for building remote procedure call (RPC) APIs. It allows different systems to communicate efficiently over a network, supporting multiple programming languages.

Key Features of gRPC:

  • Bidirectional Streaming: Enables real-time communication between clients and servers.

  • Efficient & Fast: Uses HTTP/2 for multiplexing, compression, and reduced latency.

  • Authentication & Security: Supports TLS for secure communication.

  • Load Balancing & Middleware Support: Works well with distributed systems.

Common Use Cases:

  • Microservices communication

  • Real-time applications (e.g., chat, gaming)

  • High-performance APIs for mobile and web apps

  • Cloud-based services and distributed systems

How to stream videos?

Streaming videos involves sending video data over a network in small chunks, allowing users to start watching before the entire file is downloaded. The method you choose depends on the use case (live streaming, on-demand streaming, peer-to-peer, etc.).

Types of Video Streaming:

  1. Progressive Streaming: The video file is downloaded sequentially, allowing playback before completion.

  2. Adaptive Streaming (HLS, DASH, etc.): Adjusts video quality dynamically based on network conditions.

  3. Live Streaming: Sends real-time video data to viewers.

How to Stream Videos?

1. Using HTTP-Based Streaming (HLS, DASH)

  • HLS (HTTP Live Streaming): Used by Apple devices and many modern browsers.

  • DASH (Dynamic Adaptive Streaming over HTTP): Open standard alternative to HLS.

Steps to Stream via HLS:

  1. Encode your video into multiple resolutions/bitrates.

  2. Segment the video into small .ts (transport stream) files.

  3. Generate an .m3u8 playlist file listing the segments.

  4. Serve the files via a web server or CDN.

  5. Use a video player (like Video.js, ExoPlayer) to play the stream.

2. Using RTMP (Real-Time Messaging Protocol) for Live Streaming

  • Used by platforms like YouTube Live, Twitch, Facebook Live.

  • Requires an RTMP server (e.g., NGINX with RTMP module, Wowza, Red5).

Steps:

  1. Set up an RTMP server.

  2. Use software like OBS Studio or FFmpeg to send video to the RTMP server.

  3. Distribute the stream via a streaming platform or repackage it to HLS.

3. Using WebRTC for Low-Latency Live Streaming

  • Ideal for real-time interactions (video calls, game streaming).

  • Works in browsers without extra plugins.

Steps:

  1. Capture video using WebRTC APIs.

  2. Encode and transmit using WebRTC’s peer-to-peer connections.

  3. Use a signaling server (e.g., WebSocket) to establish connections.

Tools & Libraries for Video Streaming

  • FFmpeg: Encoding, decoding, and streaming videos.

  • GStreamer: Multimedia framework for streaming.

  • Nginx with RTMP Module: For setting up an RTMP server.

  • Video.js, Plyr: Frontend players for HLS/DASH.

  • OBS Studio: Live streaming software.

What is the format in which a the video data is streamed?

The format in which video data is streamed in WebRTC depends on the encoding and transport protocols used. WebRTC does not define a specific container format like MP4; instead, it uses RTP (Real-time Transport Protocol) to transmit encoded media streams over the network.

Key Formats & Protocols in WebRTC Streaming

1. Video Encoding Formats (Codecs)

WebRTC supports these major video codecs:

  • VP8 → Default codec, efficient for most browsers.

  • VP9 → More advanced, better compression, but requires more processing power.

  • H.264 (AVC) → Widely supported, especially on mobile devices.

  • AV1 → Newer, highly efficient but not universally supported yet.

2. Audio Encoding Formats

  • Opus → Default, high-quality audio codec optimized for real-time communication.

  • G.711 → Legacy codec with wide compatibility but lower quality.

3. Transport Protocol

  • RTP (Real-time Transport Protocol) → WebRTC streams media using RTP over UDP, ensuring low latency.

  • SRTP (Secure RTP) → Adds encryption to RTP for secure transmission.

  • RTCP (RTP Control Protocol) → Monitors connection quality and provides feedback.

4. Data Format (Packetization)

  • WebRTC does not use MP4, MKV, or AVI for streaming.

  • Instead, it sends raw encoded video frames (e.g., VP8, VP9, H.264) in RTP packets.

  • These packets are decoded in real-time by the receiving browser or app.

Comparison with Other Streaming Formats

Technology Encoding Transport Latency Use Case
WebRTC VP8, VP9, H.264 RTP over UDP Ultra-low Video calls, real-time streaming
HLS H.264, HEVC HTTP (TCP) High (5-30s) Large-scale streaming (YouTube, Netflix)
RTMP H.264 TCP Low (~1-3s) Ingesting streams to YouTube/Twitch
DASH VP9, H.264 HTTP (TCP) Medium (3-10s) Adaptive streaming

Since WebRTC does not directly support MP4 streaming, we need to:

  2. Decode & transcode it to a WebRTC-compatible format (VP8, H.264, or VP9),

  3. Stream the frames to connected clients over WebRTC.

Approach

  2. Use Node.js and WebSockets for signaling.

  3. Use WebRTC PeerConnection API to stream video to the client.

2. Create the WebRTC Server (server.js)

  • Uses FFmpeg to convert MP4 into a WebRTC-compatible format.

js
const express = require("express");
const http = require("http");
const socketIo = require("socket.io");
const { spawn } = require("child_process");
const wrtc = require("wrtc");

const app = express();
const server = http.createServer(app);
const io = socketIo(server);
app.use(express.static("public")); // Serve the client page

let clients = []; // Store connected peers

io.on("connection", (socket) => {
    console.log("New client connected:", socket.id);

    socket.on("offer", async (offer) => {
        const peerConnection = new wrtc.RTCPeerConnection();
        const stream = await createFFmpegStream();
        stream.getTracks().forEach(track => peerConnection.addTrack(track, stream));

        await peerConnection.setRemoteDescription(offer);
        const answer = await peerConnection.createAnswer();
        await peerConnection.setLocalDescription(answer);
        socket.emit("answer", peerConnection.localDescription);

        peerConnection.onicecandidate = (event) => {
            if (event.candidate) {
                socket.emit("ice-candidate", event.candidate);
            }
        };

        clients.push(peerConnection);
    });

    socket.on("ice-candidate", (candidate) => {
        clients.forEach(peer => peer.addIceCandidate(candidate));
    });

    socket.on("disconnect", () => {
        clients = clients.filter(peer => peer.socket !== socket);
        console.log("Client disconnected:", socket.id);
    });
});

// Function to create a WebRTC-compatible video stream from an MP4 file
async function createFFmpegStream() {
    const ffmpeg = spawn("ffmpeg", [
        "-re",                     // Read input at native frame rate
        "-i", "video.mp4",         // Input file
        "-an",                     // Disable audio
        "-c:v", "libvpx",          // VP8 codec (compatible with WebRTC)
        "-b:v", "1M",              // Bitrate
        "-f", "webm",              // WebM container
        "pipe:1"                   // Output to stdout
    ]);

    const stream = new wrtc.MediaStream();
    const videoTrack = new wrtc.nonstandard.RTCVideoSource(ffmpeg.stdout);
    const track = new wrtc.nonstandard.RTCVideoTrack(videoTrack);
    stream.addTrack(track);
    return stream;
}

server.listen(3000, () => console.log("Server running on http://localhost:3000"));

Can grpc be used for video streaming?

gRPC is not designed for real-time video streaming. It is primarily used for efficient, high-performance communication between microservices, handling structured data efficiently over HTTP/2. However, it has limitations when it comes to real-time media streaming.

Why gRPC is NOT Ideal for Video Streaming

  1. Designed for Request-Response Communication

    • gRPC works best for structured RPC calls, not continuous media streams.

  2. No Native Support for RTP/WebRTC

    • Video streaming typically requires RTP (Real-time Transport Protocol) or WebRTC, which gRPC does not support.

  3. Based on HTTP/2, Which Is Not Optimal for Streaming

    • gRPC uses streams over HTTP/2, which introduces latency compared to protocols like UDP (used in WebRTC).

  4. Compression & Framing Issues

    • Video needs specialized codecs (e.g., H.264, VP8) and real-time packet handling, which gRPC does not optimize for.

When gRPC Can Be Used in Video Applications

While gRPC is not ideal for real-time video transmission, it can be used in supporting roles in a video streaming system:

✅ Metadata Exchange & Control Signals

  • Managing stream initiation, authentication, user preferences, or quality control settings.

✅ Chunked File Transfer (VOD, Not Live)

  • If you’re not doing real-time streaming, you can send video as binary chunks using gRPC streaming.

✅ Hybrid Approach

  • Use gRPC for control signaling (e.g., start/stop commands).

  • Use WebRTC/RTMP/HLS/DASH for actual video transmission.

Better Alternatives for Real-Time Video Streaming

Technology Use Case Protocol
WebRTC Low-latency, peer-to-peer video calls UDP + RTP
RTMP Live streaming to platforms like YouTube/Twitch TCP
HLS/DASH Large-scale video-on-demand (VOD) HTTP (Segmented)
RTP + RTSP Professional-grade live streaming UDP/TCP

Conclusion

✅ Use gRPC for signaling and metadata exchange.
❌ Do NOT use gRPC for real-time video transport.
👉 Use WebRTC, RTP, or RTMP for the actual video streaming.

What is tRPC?

tRPC (TypeScript Remote Procedure Call) is a TypeScript-first, type-safe framework for building APIs without needing a REST or GraphQL schema. It allows strongly-typed communication between a client and server using TypeScript, eliminating the need for manual API contracts.

Key Features of tRPC

✅ End-to-End Type Safety → Automatically infers types between client & server.
✅ No Boilerplate → No need to define REST endpoints or GraphQL schemas.
✅ Works with Any Frontend → Compatible with React, Next.js, Vue, and more.
✅ Built on Top of JSON-RPC → Uses function calls instead of RESTful endpoints.
✅ Lightweight and Fast → No need for extra API layers like GraphQL resolvers.

How tRPC Works

Instead of creating traditional API endpoints (GET /users, POST /order), you define procedures that the client can call like functions.

  1. Server: Define API Routes 

    ts
    import { initTRPC } from "@trpc/server";

const t = initTRPC.create();
export const appRouter = t.router({
    hello: t.procedure.query(() => "Hello, tRPC!"),
});

export type AppRouter = typeof appRouter;

  2. Client: Call the API Like a Function 

    ts
    import { createTRPCProxyClient } from "@trpc/client";
import type { AppRouter } from "./server"; // Import types from the server

const client = createTRPCProxyClient<AppRouter>({ url: "http://localhost:4000" });
const result = await client.hello.query();  // "Hello, tRPC!"

Boilerplate ✅ Minimal ❌ Requires controllers ⚠️ Needs resolvers
Performance ✅ Fast ⚠️ Varies ❌ Overhead
Schema Definition ❌ No Schema Needed ✅ OpenAPI ✅ SDL
Batch Requests ✅ Yes ❌ No ✅ Yes

What is batch reqs?

What are Batch Requests?

Batch requests allow multiple API calls to be grouped into a single request and processed together, rather than making individual requests for each piece of data. This can improve performance, reduce network overhead, and simplify the process of making multiple calls to an API.

Why Use Batch Requests?

  1. Performance Optimization:
    By grouping requests, the client can reduce the total number of network requests and response times, improving performance.

  2. Simplified Client Logic:
    Instead of handling multiple individual API calls, the client can make a single request and process the result more efficiently.

  3. Error Handling:
    Instead of managing errors for each individual request, batch processing can return all results or errors in a single response.

  4. Reduced Overhead:
    Fewer HTTP requests mean less overhead on both the client and server sides, reducing server load and response times.

How Batch Requests Work

Typically, a batch request involves wrapping multiple API calls inside a single payload, often as an array or a set of function calls. Each call will return its response in a specific order.

Example:

Batch Request Format (JSON) 

json
{
  "requests": [
    { "method": "GET", "url": "/user/1" },
    { "method": "POST", "url": "/order", "body": { "item": "laptop" } },
    { "method": "GET", "url": "/products" }
  ]
}

Response 

json
{
  "responses": [
    { "status": 200, "data": { "id": 1, "name": "John Doe" } },
    { "status": 201, "data": { "orderId": 1234, "status": "created" } },
    { "status": 200, "data": [ /* list of products */ ] }
  ]
}

How Does tRPC Support Batch Requests?

In tRPC, batch requests can be implemented by allowing the client to call multiple procedures in one go. The client can send a request with several method calls, and the server processes them and returns a batch of responses.

For example, with tRPC, the client can call multiple queries or mutations in a single request, and the server responds with each result in the same response.

Advantages of Batch Requests

  1. Less Overhead: By sending multiple requests in a single HTTP request, you reduce the total overhead for making multiple round-trips to the server.

  2. Atomicity: You can ensure that all requests are processed together. If one request fails, all the others may also be rolled back, depending on how the server handles the batch.

  3. Simplified Communication: Especially useful in applications where multiple related data points need to be fetched or modified simultaneously.

Example in GraphQL

GraphQL supports batching by allowing multiple queries or mutations to be sent in a single request. 

graphql

Batch Requests in tRPC

In tRPC, you can handle batch requests by grouping multiple procedures into a single call. While tRPC doesn’t have native support for batch requests out of the box like GraphQL, you can create a batch-like behavior by leveraging tRPC’s query and mutation system.

Basic Concept

  • tRPC allows calling multiple procedures in a single request by invoking different queries or mutations sequentially.

  • You can simulate a batch request by having the client call multiple procedures, and then the server can respond with the results of each procedure.

Example: Using tRPC to Handle Multiple Queries in One Request

1. Server Side (tRPC Router Definition)

Let’s create a basic tRPC router with multiple queries that we want to group together in a single call: 

ts
import { initTRPC } from "@trpc/server";

const t = initTRPC.create();

export const appRouter = t.router({
  getUser: t.procedure.input((id: string) => id).query((opts) => {
    // Simulate a DB fetch
    return { id: opts.input, name: `User ${opts.input}` };
  }),

  getPosts: t.procedure.query(() => {
    // Simulate fetching posts
    return [
      { title: "Post 1", content: "Content of Post 1" },
      { title: "Post 2", content: "Content of Post 2" },
    ];
  }),
});

// Export the type of the router
export type AppRouter = typeof appRouter;

2. Client Side (Batch Request Simulation)

On the client side, you can make a batch request by calling multiple procedures in a single call, using tRPC client: 

ts
import { createTRPCProxyClient } from '@trpc/client';
import { AppRouter } from './server'; // Import types from your server

const client = createTRPCProxyClient<AppRouter>({
  url: 'http://localhost:4000',
});

async function fetchBatchData() {
  try {
    // Calling multiple queries as part of the batch request
    const [user, posts] = await Promise.all([
      client.getUser.query('1'), // Call the getUser query
      client.getPosts.query(),    // Call the getPosts query
    ]);
    
    console.log('User:', user);
    console.log('Posts:', posts);
  } catch (error) {
    console.error('Error fetching data:', error);
  }
}

fetchBatchData();

Explanation:

  • The client sends a single HTTP request with multiple queries inside it (getUser.query('1') and getPosts.query()).

  • These queries are executed concurrently using Promise.all for batch execution. You could also process them sequentially if needed.

  • The server processes each query and returns the results as a combined response in one go.

Using tRPC with Batch Mutations

If you need to batch mutations, you can follow a similar approach:

1. Server Side: Define Multiple Mutations 

ts
export const appRouter = t.router({
  createUser: t.procedure.input((name: string) => name).mutation((opts) => {
    // Simulate user creation
    return { id: Math.random().toString(36).substr(2, 9), name: opts.input };

Why Use Batch Requests in tRPC?

  • Performance: Calling multiple procedures at once can reduce the number of network requests and make the application more efficient.

  • Atomicity: If using multiple mutations, you can ensure the procedures run in parallel, and then handle errors or success together.

  • Convenience: Simplifies client-side logic by grouping related requests into a single batch.

Conclusion

While tRPC doesn't have built-in support for batch requests like GraphQL, you can easily simulate batch-like behavior by calling multiple queries or mutations in parallel using Promise.all. This approach allows you to handle multiple procedures in a single network call and process them more efficiently.

Is trpc using protobufs?

No, tRPC does not use Protocol Buffers (protobufs).

Why?

tRPC is a TypeScript-first framework that focuses on type safety between the client and server. It uses TypeScript types to automatically infer the structure of your API calls, and this eliminates the need for defining additional schemas like protobufs.

With tRPC, the types you define on the server are directly accessible on the client, so there’s no need for a schema definition language (like protobufs, JSON Schema, or GraphQL schemas). The framework leverages TypeScript's type inference to automatically handle types for both the client and the server.

How Does tRPC Differ from Protobufs?

  • tRPC uses TypeScript types to generate type-safe API calls between the client and the server.

  • Protocol Buffers (protobufs) are used to define binary serialization formats for APIs and data communication between systems, often in microservices architectures. It requires manual serialization and deserialization of data and usually has to be defined in a .proto file.

Typical Use of Protobufs:

Protobufs are often used in situations where:

  1. Cross-language communication is required (e.g., a service written in Go communicates with a service in Python).

  2. Optimized binary serialization is needed for large-scale applications or microservices.

Summary

  • tRPC leverages TypeScript and provides end-to-end type safety without needing additional serialization tools like protobufs.

  • Protobufs are used for binary data serialization, and are usually applied in situations requiring cross-language data exchange or performance optimization in terms of size and speed.

If you're using tRPC, you do not need protobufs as everything is type-safe and based on TypeScript types.

What does it use transfer data behind the scenes

Under the hood, tRPC uses JSON as the default data transfer format for communication between the client and server. When a client makes a request to the server (either a query or mutation), the data is typically serialized into JSON and transmitted via HTTP (or WebSockets, depending on the setup).

How tRPC Transfers Data Behind the Scenes

  1. Client-Server Communication:
    When a client calls a procedure (query or mutation) on the server, the client sends the request to the server, and the server processes the request. The input data (e.g., parameters or payload) is serialized to JSON format and sent over HTTP or WebSockets.

  2. Request Format:
    A typical request in tRPC is sent as a JSON object, containing information about the procedure being called, its arguments, and any other required metadata.

    For example, when calling a query: 

    json
    {
  "jsonrpc": "2.0",
  "method": "getUser",
  "params": ["1"],
  "id": "12345"
}

    • "jsonrpc" specifies the version.

    • "method" is the procedure being called (getUser in this case).

    • "params" contains the parameters for the procedure (["1"] for the user ID).

    • "id" is used for tracking the request (especially useful when batching requests).

  3. Response Format:
    Once the server processes the request, it sends a JSON response back to the client, typically containing the result or any error information.

    For example: 

    json
    {
  "jsonrpc": "2.0",
  "result": { "id": "1", "name": "John Doe" },
  "id": "12345"
}

  4. Serialization:

    • Data is serialized to JSON on both the client and server sides. This is the most common format for web APIs because of its ease of use, human-readability, and support in almost all programming languages.

  5. HTTP / WebSocket:
    By default, tRPC uses HTTP to transfer data between the client and the server. However, it can also be configured to use WebSockets for real-time communication, where the same JSON-based communication is used but over a persistent connection.

Why JSON?

  • Interoperability: JSON is supported by almost all modern web frameworks, making it easy to integrate with existing applications.

  • Human-readable: JSON is text-based and easy to debug, which is a big advantage during development.

  • TypeScript Support: Since tRPC is designed for TypeScript-first applications, working with JSON makes sense as it is compatible with TypeScript’s type system and easy to handle natively.

What Happens in the Background?

  1. The client sends a JSON-encoded request to the server (e.g., via HTTP POST or WebSocket message).

  2. The server processes the request using the specified procedure (query or mutation), and the response data is JSON-encoded and sent back to the client.

  3. Both client and server communicate over a text-based protocol (JSON) over HTTP (or WebSockets), making it simple and efficient.

Is This Different from Other APIs?

In contrast to frameworks like gRPC that use Protocol Buffers (protobufs) for efficient binary serialization, tRPC sticks with JSON for simplicity, ease of use, and full compatibility with TypeScript. While gRPC focuses on performance optimizations, tRPC focuses on developer experience and seamless integration with TypeScript.

Summary

  • tRPC uses JSON as the format for serializing and transferring data between the client and server.

  • Data is sent via HTTP or WebSocket using JSON-encoded requests and responses.

  • This approach makes tRPC easy to use in TypeScript-based applications while offering a clean and efficient communication protocol for most web-based applications.

Implement grpc in node js

To implement gRPC in Node.js, you'll need to follow a few steps. Here's a simple guide to help you set up a gRPC server and client in Node.js.

1. Install Required Packages

First, you'll need to install gRPC and Protobuf dependencies. You can install them using npm: 

bash
npm install @grpc/grpc-js @grpc/proto-loader

  • @grpc/grpc-js: The gRPC library for Node.js.

  • @grpc/proto-loader: A utility for loading .proto files (Protocol Buffers).

2. Create the Protobuf File (.proto)

Create a file called service.proto to define the gRPC service and message structure. 

proto
// service.proto

syntax = "proto3";

package example;

// The service definition
service Greeter {
  // Sends a greeting
  rpc SayHello (HelloRequest) returns (HelloReply);
}

// The request message containing the user's name
message HelloRequest {
  string name = 1;
}

// The response message containing the greetings
message HelloReply {
  string message = 1;
}

This defines a simple Greeter service with a method SayHello, which takes a HelloRequest and returns a HelloReply.

3. Implement the gRPC Server

Now let's implement the server using the @grpc/grpc-js library in Node.js. 

js
// server.js

const grpc = require('@grpc/grpc-js');
const protoLoader = require('@grpc/proto-loader');

// Load the protobuf file
const PROTO_PATH = './service.proto';
const packageDefinition = protoLoader.loadSync(PROTO_PATH, {});
const protoDescriptor = grpc.loadPackageDefinition(packageDefinition);
const greeter = protoDescriptor.example.Greeter;

// Implement the SayHello function
function sayHello(call, callback) {
  const name = call.request.name || 'World';
  callback(null, { message: `Hello, ${name}!` });
}

// Create the gRPC server
const server = new grpc.Server();

// Add the service to the server
server.addService(greeter.service, {
  SayHello: sayHello,
});

// Start the server on port 50051
server.bindAsync('127.0.0.1:50051', grpc.ServerCredentials.createInsecure(), () => {
  console.log('Server running at http://127.0.0.1:50051');
  server.start();
});

4. Implement the gRPC Client

Now, implement the client that will communicate with the server. 

js
// client.js

const grpc = require('@grpc/grpc-js');
const protoLoader = require('@grpc/proto-loader');

// Load the protobuf file
const PROTO_PATH = './service.proto';
const packageDefinition = protoLoader.loadSync(PROTO_PATH, {});
const protoDescriptor = grpc.loadPackageDefinition(packageDefinition);
const greeter = protoDescriptor.example.Greeter;

// Create a client
const client = new greeter('localhost:50051', grpc.credentials.createInsecure());

// Make a call to the SayHello method
client.SayHello({ name: 'Node.js' }, (error, response) => {
  if (error) {
    console.error(error);
  } else {
    console.log('Greeting:', response.message);
  }
});

5. Running the Server and Client

  1. Run the Server:

    In one terminal window, run the server: 

    bash
    node server.js

    The server should start and listen on localhost:50051.

  2. Run the Client:

    In another terminal window, run the client: 

    bash
    node client.js

    The client will call the SayHello method of the server and you should see a response like: 

    Greeting: Hello, Node.js!

Explanation of Key Steps

  • Protobuf File (.proto): Defines the structure of messages and services, including the SayHello method.

  • Server:

    • Loads the protobuf definition using @grpc/proto-loader.

    • Implements the method sayHello that responds to the SayHello request.

    • Binds the server to localhost:50051.

  • Client:

    • Loads the protobuf definition and creates a client.

    • Sends a SayHello request with the name "Node.js" and prints the response.

Conclusion

This example shows how to set up a simple gRPC server and client in Node.js. You can expand on this by adding more complex services and methods, handling errors, and using secure communication with SSL/TLS for production environments.

Steps to Call a tRPC API from Another Application:

  1. Set Up the tRPC Server:
    If you haven’t already, you need a tRPC server running. Here's a simple setup using Next.js and tRPC:

    • Install tRPC Dependencies: 

      bash
      npm install @trpc/server @trpc/client

      ts
      // appRouter.ts
import { createRouter } from '@trpc/server';

    input: z.string(),

    input: z.object({

    }),
    resolve({ input }) {
      // Simulate user creation

    This sets up a simple tRPC server with a couple of procedures (getUser, createUser).

  2. Calling tRPC from Another Application:
    To call the tRPC API from an external application, you’ll be interacting with the HTTP API endpoints exposed by the tRPC server.

    Here’s how you can call the tRPC API from another application using HTTP requests.

callTrpc();

      In this example:

      • We're sending a POST request to the tRPC API with jsonrpc, method, params, and id.
