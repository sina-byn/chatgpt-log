You're close! But the problem with your current Permutation type is that it recursively references itself without narrowing the set, which causes an infinite type expansion. TypeScript doesn't allow unrestricted recursive type definitions like this.

To generate all possible permutations of string unions like 'hover' | 'active' | 'before' | 'after', you need to:

  1. Use conditional types.

  2. Exclude the current item from the next recursive call to avoid infinite loops.

Here's the correct way to define it: 

ts
type Modifier = 'hover' | 'active' | 'before' | 'after';

type Permutation<S, T = S> =

    : S extends T

      : never;

  • Exclude<T, S>: Ensures we don't include the same element twice.

Explain the logic behind S extends T

Great question! Let's break down the logic behind S extends T in this context. Understanding this will help you see how recursive permutation types work in TypeScript.

🔍 S extends T — What it really means here

In this line: 

ts
S extends T

We're iterating over each element of the union T using S. It’s a trick to map each member of a union one by one.

But to really understand how this works, let’s break it down step by step.

🧠 Think of a union as a set 

ts
type Modifier = 'hover' | 'active' | 'before' | 'after';

We want to go through each item ('hover', 'active', etc.) and for each one, create permutations using the remaining ones.

👇 So what's happening in this line? 

ts
S extends T
  ? `${S}` | `${S}-${Permutation<Exclude<T, S>>}`
  : never;

Let’s say T = 'hover' | 'active' | 'before' at some point. Now we loop through S by extending T.

This expands to: 

ts
'hover' extends 'hover' | 'active' | 'before' 
  ? 'hover' | `hover-${Permutation<'active' | 'before'>}`
: never;

'active' extends 'hover' | 'active' | 'before' 
  ? 'active' | `active-${Permutation<'hover' | 'before'>}`
: never;

'before' extends 'hover' | 'active' | 'before' 
  ? 'before' | `before-${Permutation<'hover' | 'active'>}`
: never;

That gives us all permutations starting with:

  • hover, hover-active, hover-active-before, ...

  • active, active-hover, active-hover-before, ...

  • and so on...

So we are saying:

"For each S in T, give me S plus all permutations of the rest of T excluding S."

✅ Why it works

Because in TypeScript, when you write: 

ts
S extends T ? ... : ...

and S is itself a union (like 'hover' | 'active'), TypeScript distributes the conditional across each element of S. That’s what allows this type-level loop.

Bonus: Exclude<T, S>

That’s what removes the currently used item (S) so we don’t repeat values in the permutation.

Example: 

ts
Exclude<'hover' | 'active', 'hover'> = 'active'

TL;DR

  • S extends T is looping through each item in the union T.

  • For each S, it creates:

    • ${S}: the standalone

    • ${S}-${Permutation<...>}: recursive combinations with the rest

  • Exclude<T, S> ensures no repeats.

  • The recursion continues until the union is empty (never), which is the base case.

🚀 What "distribution" means in conditional types

Let’s start with a simple conditional type: 

ts
type A<T> = T extends string ? true : false;

If you do: 

ts
type Test = A<'hello'>; // ✅ true

Makes sense, right?

But what if T is a union? 

ts
type Test = A<'hello' | 123>;

Now here’s the twist:
TypeScript will distribute the conditional type across each member of the union, like this: 

ts
A<'hello'> | A<123>
=> true | false

So:

ts
type Test = true | false; // ✅ That's the result!

This behavior is intentional and allows many advanced type tricks.

🧪 Why this matters for permutations

Let’s say you define: 

ts
type Modifier = 'hover' | 'active';

type MyType<S> = S extends Modifier ? `:${S}` : never;

type Result = MyType<'hover' | 'active'>;

Even though you passed a union ('hover' | 'active') to MyType, what TypeScript actually does is: 

ts
MyType<'hover'> | MyType<'active'>
=> ':hover' | ':active'

That’s what we mean by:

"TypeScript distributes the conditional across the union."

🔁 Why this allows a "type-level loop"

When we do: 

ts
S extends T
  ? `${S}` | `${S}-${Permutation<Exclude<T, S>>}`
  : never;

// then S = 'active'
'active' extends T ? 'active' | 'active-' + Permutation<...> : never
//
// then S = 'before'
...

So each branch of the union gets processed individually and merged back into a final result.

This is not recursion in the traditional sense — it's distribution + recursive type call, and that’s what makes permutation types possible.

🧠 First, let's revisit the pattern: 

ts
type Permutation<S, T = S> = 
  [S] extends [never]
    ? ''
    : S extends T
      ? `${S}` | `${S}-${Permutation<Exclude<T, S>>}`
      : never;

Here:

  • T is the full original union ('hover' | 'active' | ...).

  • S is the current item we’re iterating through.

The key idea is:

We want to go through each S in the union T, and for each one, build a permutation with the remaining items.

So the question is:

❓ Why S extends T, not T extends S?

Let’s break it down:

S extends T ✅ Means: take each S from union T and build something with it
T extends S 🚫 Would mean: does the full union T match each individual S? That’s not helpful or distributive

Example: 

ts
type Modifier = 'hover' | 'active';

type Bad<T> = T extends 'hover' ? true : false;
type BadTest = Bad<'hover' | 'active'>; // ✅ Distributes

// But if you flip it:
type Weird<T> = 'hover' extends T ? true : false;
type WeirdTest = Weird<'hover' | 'active'>; // ✅ Still true, but no distribution

See the difference?

  • S extends T lets you loop through union members one by one ('hover', 'active', etc.) — this is distributive.

  • T extends S checks: “does 'hover' | 'active' extend 'hover'?” (No! So this fails.)

🔄 And in the context of permutations?

You're trying to do:

For each S in the union T,
add ${S} to ${Permutation<Exclude<T, S>>}

So the structure must be: 

ts
S extends T

Which tells TypeScript:

“Hey, for each S inside T, go ahead and create a permutation branch with S.”

If you wrote T extends S, you’re essentially saying:

“For this one S, does the entire union T match or extend it?”
That’s a yes/no question, not a for-each loop.

✅ TL;DR

Why S extends T? Because we want to distribute over each S in union T.
Why not T extends S? That would not iterate. It would just test a full match.
What does this enable? Distributive conditional types → essential for permutations.

Why [S] extends [never] ?

🔥 That’s one of the most clever tricks in TypeScript’s type system — and your curiosity is 100% on point!

Let’s break it down:

❓ Why do we write [S] extends [never] instead of just S extends never?

✅ First: What we’re doing

In this line: 

ts
[S] extends [never] ? '' : ...

We’re checking if the union S is empty (i.e., never).
This tells us we’ve reached the end of recursion — a base case.

🧨 But here’s the twist:

If you write: 

ts
S extends never ? ... : ...

It behaves differently than you'd expect when S is a union.

For example: 

ts
type T = 'a' | 'b';
type X = T extends never ? true : false;
// ❌ Result: false

You might think:

"If T is not never, then this should just be false."

True... but there’s a hidden issue when S is a union: TypeScript distributes conditional types over unions.

So:

ts
S extends never ? ... : ...

becomes:

ts
('a' extends never ? ... : ...) |
('b' extends never ? ... : ...)

Each branch is false, so the result is false.
But that's not the question we were trying to ask.

We wanted to ask:

“Is the whole union S equal to never?”
But S extends never ends up checking: “Are each of the members of S assignable to never?” – which they are not.

🧠 So what’s the solution?

We wrap it in a tuple: 

ts
[S] extends [never]

Now it's not distributive anymore.
Why? Because TypeScript only distributes conditional types over naked type parameters — not when they’re wrapped.

So:

ts
[S] extends [never]

is evaluated once, as a whole.

📌 Real example: 

ts
type T1 = 'a' | 'b';
type T2 = never;

type A = T1 extends never ? true : false;  // false (but distributed!)
type B = [T1] extends [never] ? true : false; // false ✅

type C = [T2] extends [never] ? true : false; // true ✅

So now we can safely check:

"Is this union S completely empty?"
→ Meaning: Have we finished the recursive breakdown?

✅ TL;DR

Expression Meaning
S extends never ✅ Checks each member of S separately (distributes over union) — not what we want
[S] extends [never] ✅ Checks if the whole type S is literally never — this is what we need

Limiting the depth of recursive permutations in TypeScript (e.g., to max 2 words like "hover-active") is totally doable — but it requires adding a "depth counter" to the recursion.

✅ Goal:

Instead of getting: 

ts
"hover"
"hover-active"
"hover-active-before"
"hover-active-before-after"
// ❌ too deep

You want to stop after 2 elements: 

ts
"hover"
"hover-active"
"active-before"
...
// ✅ no 3-word combinations

🛠 Solution: Add a depth parameter

We can pass a tuple to count recursion depth — TypeScript tracks tuple length for free! 

ts
type Modifier = 'hover' | 'active' | 'before' | 'after';

type Permutation<
  S extends string,
  T extends string = S,
  D extends any[] = [] // 👈 depth counter
> =
  [S] extends [never]
    ? ''
    : D['length'] extends 2 // 👈 stop at depth 2
      ? `${S}`
      : S extends T
        ? `${S}` | `${S}-${Permutation<Exclude<T, S>, Exclude<T, S>, [...D, 1]>}`
        : never;

🔍 Explanation:

  • D is a tuple that grows with each recursive step ([...D, 1])

  • D['length'] tracks how many steps deep we are

  • We stop recursion if depth = 2, and return only ${S}

  • Otherwise, we keep building ${S}-${...}

🔁 Example Output (type P): 

ts

"hover-before"
"hover-after"

"active-before"
...

❌ But not things like "hover-active-before" or "before-hover-active-after"

✅ TL;DR

To limit permutation depth:

  • Use a D extends any[] parameter as a counter

  • Use D['length'] extends 2 (or any number) as your depth limit
