Lamport clock explanation

What is a lamport clock?

A Lamport clock is a logical clock used in distributed systems to order events when there is no shared global clock ⏱️. It was introduced by Leslie Lamport.

The key idea:

If one event causally happens before another, the Lamport clock assigns a smaller timestamp to the first event.

Why Lamport clocks are needed

In distributed systems:

  • Each machine has its own local clock

  • Clocks can drift or be unsynchronized

  • We still need a way to reason about event ordering

Lamport clocks solve this by tracking causality, not real time.

How Lamport clocks work

Each process maintains a counter (integer).

Rules

  1. Local event
    Increment the clock before the event 

    clock = clock + 1

  2. Sending a message
    Increment clock and attach the timestamp to the message

  3. Receiving a message
    Set clock to: 

    clock = max(local_clock, received_timestamp) + 1

Example

  • Process P1 sends a message at time 5

  • Process P2 receives it while its clock is 3

  • P2 updates its clock to max(3,5) + 1 = 6

This guarantees:

The receive event happens after the send event.

What Lamport clocks guarantee ✅

  • If A happens-before B, then 

    time(A) < time(B)

What Lamport clocks do NOT guarantee ❌

  • They cannot detect concurrent events

  • If time(A) < time(B), it does not necessarily mean A caused B

To detect concurrency, you need Vector Clocks.

Where Lamport clocks are used

  • Distributed databases

  • Event ordering in distributed logs

  • Mutual exclusion algorithms

  • Debugging distributed systems

One-sentence summary

A Lamport clock is a logical counter that orders events in a distributed system based on causal relationships, not real time.

Explain the issue with concurrency - keep it short though

Concurrency issue with Lamport clocks (short):

Lamport clocks cannot tell if two events are concurrent.
If event A has a lower timestamp than B, it doesn’t mean A caused B—they may have happened independently on different processes.

How to fix that then?

Use Vector Clocks ✅

Why they fix it:
Vector clocks keep a separate counter per process, not just one number.

  • They can tell if A → B (causal)

  • They can tell if A ∥ B (concurrent)

Rule (simple):

  • If all entries in V(A) ≤ V(B) and at least one is <, then A happened before B

  • If neither vector ≤ the other, the events are concurrent

👉 Lamport clocks order events; vector clocks also detect concurrency.

Vector Clock — step-by-step

Each process keeps a vector of counters (one entry per process).

1️⃣ Local event

Increment your own entry in the vector 

VC[i] = VC[i] + 1

2️⃣ Sending a message

  • Increment your own entry

  • Attach the entire vector to the message 

VC[i]++
send(message, VC)

3️⃣ Receiving a message

  • For each position k, take the max

  • Increment your own entry 

for each k:
  VC[k] = max(VC[k], receivedVC[k])

VC[i]++

4️⃣ Comparing two events

  • A → B if VC(A) ≤ VC(B) and at least one <

  • Concurrent if neither vector ≤ the other

In short:
Vector clocks extend Lamport clocks by tracking who caused what, not just order 🧠

Give me a simple implementation in js

Here’s a simple JavaScript implementation of vector clocks for a few processes: 

javascript
class VectorClock {
  constructor(processCount, processId) {
    this.processId = processId;            // ID of this process
    this.clock = Array(processCount).fill(0); // Initialize vector clock
  }

  // Local event
  tick() {
    this.clock[this.processId]++;
  }

  // Sending a message
  send() {
    this.tick(); // increment before sending
    return [...this.clock]; // send a copy of the vector clock
  }

  // Receiving a message
  receive(receivedClock) {
    for (let i = 0; i < this.clock.length; i++) {
      this.clock[i] = Math.max(this.clock[i], receivedClock[i]);
    }
    this.tick(); // increment after merging
  }

  // Compare clocks
  static compare(a, b) {
    let less = false;
    let greater = false;

    for (let i = 0; i < a.length; i++) {
      if (a[i] < b[i]) less = true;
      if (a[i] > b[i]) greater = true;
    }

    if (less && !greater) return "A happened before B";
    if (greater && !less) return "B happened before A";
    if (!less && !greater) return "A and B are identical";
    return "A and B are concurrent";
  }
}

// Example usage:
const p0 = new VectorClock(3, 0);
const p1 = new VectorClock(3, 1);

p0.tick(); // local event at P0
let msg = p0.send(); // P0 sends message

p1.receive(msg); // P1 receives message

console.log("P0 clock:", p0.clock);
console.log("P1 clock:", p1.clock);

// Compare two clocks
console.log(VectorClock.compare(p0.clock, p1.clock));

Explanation:

  • Each process maintains a vector of size = total processes

  • tick() increments the local counter

  • send() attaches the vector to messages

  • receive() merges incoming vector clocks and increments local counter

  • compare() tells if events are causal or concurrent

explain the compare method throughly

Absolutely! Let’s break down the compare method in the vector clock implementation step by step. This method is crucial because it determines the causal relationship between two events.

1️⃣ Purpose

The compare(a, b) method checks the relationship between two vector clocks a and b:

  • Happened-before (→): one event causally precedes the other

  • Concurrent: the events are independent

  • Identical: clocks are exactly the same

2️⃣ How it works

js
let less = false;
let greater = false;

for (let i = 0; i < a.length; i++) {
  if (a[i] < b[i]) less = true;
  if (a[i] > b[i]) greater = true;
}

  • less becomes true if any entry in a is smaller than b

  • greater becomes true if any entry in a is larger than b

  • We track both flags while iterating through all processes

3️⃣ Determining the relationship 

js
if (less && !greater) return "A happened before B";
if (greater && !less) return "B happened before A";
if (!less && !greater) return "A and B are identical";
return "A and B are concurrent";

  • less && !greater → All entries in a ≤ b, and at least one < → A → B

  • greater && !less → All entries in b ≤ a, and at least one < → B → A

  • !less && !greater → Every entry is exactly equal → identical events

  • Otherwise → Neither vector dominates the other → events are concurrent

4️⃣ Example

Suppose we have two vector clocks for 3 processes: 

a = [1, 2, 0]
b = [2, 2, 0]

Step by step:

i a[i] b[i] less greater
0 1 2 true false
1 2 2 true false
2 0 0 true false

  • less = true, greater = false → A happened before B

Another example:

a = [1, 0, 2]
b = [0, 1, 2]

Step by step:

i a[i] b[i] less greater
0 1 0 false true
1 0 1 true true
2 2 2 true true

  • Both less and greater are true → A and B are concurrent

✅ Key takeaway:
Vector clocks allow us to detect causality and concurrency, unlike Lamport clocks. The compare method does this by checking if one vector dominates the other or not.

Are these used nowadays or not?

Yes, vector clocks are still used today, but their usage depends on the system’s needs. They’re less common in general-purpose apps because they’re more complex and require tracking a counter per process, but they’re important in distributed systems where you need causal consistency or conflict detection.

Where they are used nowadays:

  1. Distributed databases & storage systems

    • Example: Amazon DynamoDB, Cassandra, Riak

    • Vector clocks help detect conflicting updates (e.g., two users update the same item concurrently).

  2. Version control / CRDTs (Conflict-free Replicated Data Types)

    • Keep track of causal history of changes to merge edits correctly.

  3. Messaging systems / Event logs

    • Ensure causal ordering of events across nodes.

  4. Debugging & tracing distributed systems

    • Tools may use vector clocks to understand event causality and concurrency.

Limitations / Why they aren’t everywhere

  • The vector grows with the number of processes, which can be large in modern cloud systems

  • Maintaining it can become expensive

  • Often, systems use Lamport clocks or hybrid approaches for efficiency, unless precise concurrency tracking is required

💡 Summary: Vector clocks are still relevant, especially in distributed databases and CRDT-based systems, but for many applications, simpler logical clocks or timestamps are preferred.
